# Glossary — термины продукта TestAI

Источник правды по терминологии. Пополняй по мере обсуждений; дубли в TeamStorm-вики
сверяй и своди сюда. Каждый термин — атомарно, одной формулировкой.

## Продукт

- **TestAI / QATO** — платформа, автоматизирующая создание UI e2e-тестов: читает
  ручные тест-кейсы из существующей TMS и генерирует исполняемый код автотестов.
- **TMS** — Test Management System. Первая интеграция — [[constraints|Test IT]] (партнёр).
- **Recipe (рецепт)** — структурированный промежуточный артефакт между шагами теста
  и финальным кодом. Делает сгенерированный код поддерживаемым и ревьюабельным.
- **Автотест** — сгенерированный Playwright JavaScript-код для интеграции в репозиторий тестов.

## Исполнение

- **Execution model** — система выполняет шаги теста, наблюдая за своими действиями
  в реальном браузере (клики, ввод, навигация, валидации) → рецепт → код.
- **LLM + LVM** — на каждом шаге скриншот → модель анализирует экран → выбирает действие.
- **Visual Editor** — no-code интерфейс ревью/правки тестов; работает как [[constraints|VNC]]-десктоп с браузером.

## Статусы (единая сетка, шаг и рецепт/сегмент — источник QATO-650 §2.1)

- **Draft** — черновик, предикция не делалась (только шаг).
- **Unverified / «не подтверждён»** — код сгенерирован, но не прогнан/не подтверждён (только шаг).
- **Verified / «готов»** — прогнан и подтверждён (только шаг).
- **New / «Новый»**, **NeedsWork / «Требует доработки»** (есть неподтверждённые/сломанные шаги),
  **Ready / «Готово»** (все шаги Verified), **InProgress / «В процессе»** (идёт генерация/запись/
  прогон — редактирование НЕ «В процессе») — уровень рецепта/сегмента.
- ⚠️ **Не вводим параллельные слова** «отладка / отлаженный / проверено» как отдельный смысл — это
  тот же Verified/готов под другим ярлыком. UI-копирайт вроде «без повторной отладки», «отлаженные
  шаги», «N шагов · проверено» — приводить к «готов»/Verified. Источник разнобоя: старые прототипы
  до канона 14.07; см. [[QATO-1671]] обсуждение 2026-07-16.

## Сегмент и модель Input/Output (источник QATO-650 §2, §4.1; открытый UX — см. [[QATO-1671]])

- **Сегмент** — готовый (Verified) переиспользуемый набор из одного и более шагов, вынесенный из
  рецепта и применяемый в других тест-кейсах. Устроен как функция: Input (что нужно на вход) →
  Output (что отдаёт наружу). Применяется **как код**, без повторной генерации.
- **Предусловие** — частный случай сегмента: стоит в начале теста, Input пустой (только env-переменные
  проекта, не переменные конкретного теста). Постусловие — сегмент в конце. Позиция определяет тип,
  это не отдельная сущность.
- **Input** — именованная переменная, которую сегмент требует на входе от рецепта-хозяина (аналог
  параметра функции): без неё сегмент не может выполниться корректно. Пример: сегмент «Войти под
  ролью» → Input `role`. В MVP (Задача 1) Input всегда пуст (только env) — маппинг Input к
  переменным конкретного рецепта появляется в след. итерации.
- **Output** — именованная переменная, которую сегмент отдаёт наружу после выполнения — становится
  доступна остальным шагам рецепта (аналог возвращаемого значения функции). Пример: сегмент
  «Авторизация» → Output `sessionToken`; «Создать новость» → Output `newsId`. Вне MVP (след. итерация).
- **Внутренние (scoped) переменные сегмента** — нужны только внутри самого сегмента, не входят в
  Input/Output и не «протекают» наружу (изоляция — поведение рантайма, а не сокрытие в UI: в
  интерфейсе внутренние переменные и Input/Output пользователю видны, чтобы можно было самостоятельно
  дебажить — решение 14.07).
- **By-ref (по ссылке)** — рецепт хранит не копию шагов сегмента, а ссылку на него; правка сегмента в
  одном месте отражается во всех связанных рецептах. Материализация — разворот ссылки в собственные
  inline-шаги конкретного рецепта (при отвязке или удалении сегмента).

## Окружение / стенды (источник [[QATO-1483]], в проработке)

- **Стенд (окружение)** — именованный контур, на котором прогоняется тест: SUT URL + набор значений
  env-переменных. Сегодня в проекте ровно один (`Project.sutUrl` + `Project.envData`); мультистенды
  ([[QATO-1483]]) вводят несколько стендов на проект с выбором активного на прогон.
- **Модель стендов (решено 2026-08-13):** стенды **независимы**, каждый несёт свой набор
  переменных (ключи+значения) + свой URL. Драйвер: у многих QA персональные стенды. Цена: если
  стенд не содержит ключа, на который ссылается рецепт (`[[key]]`), шаг не резолвится → нужна
  обработка в UX.
- **SUT URL (`sutUrl`)** — базовый адрес системы под тестом; база для навигации и API-запросов
  (`apiRequestUrl.ts`). Часть стенда.

## адаптация тест-кейса

Операция переработки ручного тест-кейса так, чтобы агент смог сгенерировать по нему автотест:
разворот склеенных шагов, объект и начальное состояние, вынос подготовки данных в предусловия,
конкретизация ожидаемых результатов, пометки непригодных шагов. Один кейс на входе — один на выходе.

Термин **предложен 31.07 и ещё не подтверждён**. Отвергнутые варианты: «оптимизация» (обещает
улучшение вообще, а мы делаем кейс пригодным для генерации, иногда теряя покрытие), «подготовка»
(слово занято подготовкой данных в предусловиях), «нормализация» (остаётся названием эпика
[[QATO-1897]], в продукте не используется).

Внутренний этап операции, который находит дефекты по чеклисту, называется **проверкой**: отдельной
операцией «анализ» в первом этапе не выводится.
