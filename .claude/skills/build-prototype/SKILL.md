# Prototype Generator для Test AI

Финальный слой дизайн-процесса (см. `CLAUDE.md`, «Слои работы»): кликабельный прототип
для валидации сценария и показа стейкхолдерам. **Прототипы никогда не идут в продакшен.**

## Входные данные

- Сценарий / user flow из `wiki/scenarios/` (или текстом/ссылкой)
- DESIGN.md — единственный источник правды по визуалу
- Реальный экран в `../qato/qautomator-ui` — основа структуры
- Опционально: PRD, AC, скриншоты текущего UI для контекста

## Выход

Папка `prototypes/QATO-XXXX-slug/` с `index.html` как точкой входа. Golos Text через Google
Fonts, Lucide через CDN. Если flow сложный и один файл становится нечитаемым — допускается
разбивка на несколько HTML с перелинковкой. По умолчанию — один `index.html`.

## Старт: kit, а не с нуля

⚠️ **Не переэмичивай бойлерплейт.** Токены DESIGN.md, оболочка (rail/content-card/sidebar),
scenbar, кнопки/бейджи/меню/модалки/тосты и рантайм вынесены в `prototypes/_kit/`
(`tokens.css` + `shell.css` + `proto.js`). Начинай каждый прототип с бутстрапа:

```bash
bash prototypes/_kit/new.sh QATO-XXXX-slug
```

Это создаёт папку задачи с копиями kit-ассетов и стартовым `index.html` (scenbar + рейл +
пустой content-card уже на месте, иконки/переключение состояний работают). Папка
самодостаточна для per-folder деплоя. Полная памятка по kit и хелперам — `prototypes/_kit/README.md`.

Дальше пишешь только то, что специфично для задачи: наполняешь `<select>` и `window.SCEN`,
вставляешь скелет экрана, доопределяешь `window.applyScenario(id)`. **Стили под задачу** —
в инлайновый `<style>` поверх kit; не дублируй то, что уже в `shell.css`.

**Скелет экрана:** сперва смотри `prototypes/_kit/screens/<screen>/` — прод-верные шаблоны,
замороженные из живого Storybook (реальный DOM под `prod.css`, идентично проду). Есть — копируй
разметку оттуда и подключи `prod.css`; это даёт кожу без ручного перевода. Нет нужного экрана —
добавь его через скилл `refresh-templates` (сними живой компонент/страницу в библиотеку), а не
рисуй по мотивам. ⚠️ Шаблоны генерируются, руками не правь; для редизайна не принимай шаблон за
данность (его модель и надо менять). См. `[[feedback-prototype-fidelity]]`,
`[[feedback-prototype-redesign-model]]`.

**Новая интерактивность — от аналогов, не с нуля.** То, чего ещё нет в проде (ради чего и делается
редизайн), собирай на базе существующих паттернов: ближайший шаблон из `screens/`, story
компонента в Storybook, паттерн из DESIGN.md. Нашёл аналог — бери его разметку/поведение за основу
и адаптируй; кожа всё равно из `prod.css`. Не изобретай вид и поведение произвольно
(`[[feedback-new-interactivity-from-analogues]]`).

## Баннер управления сценариями (обязателен для каждого прототипа)

Уже в kit-шаблоне (`_template/index.html` → копируется бутстрапом). Тёмная панель
(`--bg-solid`, grid `1fr auto 1fr`): слева ключ задачи + pill `прототип` (без «не продакшен»);
по центру `<select id="scen-select">` (группируй `<optgroup>` по экранам) и сразу за ним
стрелки ‹ › (`data-action="prev-scen|next-scen"`); справа `data-action="reset"`. Листание и
переключение состояний делает `showScenario(id)` из `proto.js` по массиву `window.SCEN` —
тебе нужно только наполнить `<select>` и `SCEN`. Подпись «Сценарий:» не добавляй.

## Частые ловушки (проверяй перед сдачей)

- **Дропдауны/меню обрезаются контейнером.** Любой предок с `overflow: hidden|auto|clip`
  (а в нашем layout их много: content card, список, секция) обрезает абсолютно
  спозиционированных потомков. ⚠️ Ловился на этом в QATO-1671 ДВАЖДЫ.
  **Фикс уже в kit:** открывай меню через `openMenu(menuEl, btn)` (или атрибутами
  `data-action="kebab" data-menu="#id"`) — оно рендерится `position:fixed` по rect кнопки и не
  обрезается. `position:absolute` внутри карточки/строки не использовать никогда.
- **Тултип уходит за край и обрезается.** У верхних элементов (хедер) тултип над кнопкой режется —
  используй `.tip-wrap.tip-below` (kit показывает тултип снизу).
- Прототип десктопный — смотри в широком вьюпорте (≥1280px), узкий рейл схлопывает колонки.

## Смоук перед каждым пушем (обязательно)

`smoke()` живёт в kit (`proto.js`): прогоняет все состояния из `window.SCEN`, ловит ошибки JS и
рассинхрон навигации (когда стрелки ‹ › не переключают на нужное состояние). **Перед любым коммитом
прототипа прогони смоук и убедись, что он зелёный.** Это экономит пользователю время на ручную
проверку кликабельности.

Как прогнать:
- открыть прототип в Chrome пользователя (хостовый `http.server`), в адресе добавить `#smoke`
  (авто-прогон) или вызвать `smoke()` в консоли; в консоли ждём `✅ смоук: N состояний, ошибок нет`;
- либо, если поднят claude-in-chrome и вкладка с прототипом открыта, выполнить `smoke()` через
  `javascript_tool` и прочитать результат.

Если состояний не по одному `.screen` на сценарий (например одна поверхность обслуживает несколько
состояний через `applyScenario`), переопредели `currentScenario()` на трекер текущего id, иначе смоук
законно поймает рассинхрон стрелок.

## Правила генерации

1. **Два источника истины — раздели их.** Скелет (структура, layout, состояния, набор и
   иерархия компонентов) берётся из реального экрана в `../qato/qautomator-ui` — см.
   `wiki/product/screens-map.md`, какой экран клонировать. Кожа (токены цветов, типографика,
   spacing, border-radius, shadows) — строго из DESIGN.md. Репа и DESIGN.md собраны на одном
   стеке (Radix + shadcn + Tailwind), поэтому компоненты ложатся 1:1. Не изобретай ни структуру, ни стили.
   ⚠️ **Цель — 1 в 1 с продом, минимум различий.** Скелет бери из РЕАЛЬНЫХ компонентов
   (читай `.tsx` + `.styles.ts` вглубь: под-компоненты, классы, размеры, состояния), а НЕ из
   ранее собранных прототипов и не «по мотивам» — иначе разойдётся с продом. Не уверен в
   структуре экрана — разбери его параллельными Explore-агентами до сборки. Финально сверяй
   прототип с реальным экраном, а не только с DESIGN.md. (см. [[feedback-prototype-fidelity]])
2. Flow из нескольких экранов — навигация через JS (табы, «Далее/Назад», sidebar — по сценарию).
3. Интерактивность: кликабельные кнопки, переходы между состояниями, модалки, hover.
   Данные захардкожены, но реалистичны и на русском.
4. Layout: паттерн из DESIGN.md (icon rail 56px + content card с sidebar 320px + main area),
   если сценарий предполагает работу внутри приложения.
5. Lucide иконки: только из Lucide, через CDN (`unpkg.com/lucide`).
6. Шрифт Golos Text — через `fonts.googleapis.com`.
7. Без фреймворков (React, Vue). Чистый HTML + CSS + vanilla JS.
8. Монорепа `../qato` — ОБЯЗАТЕЛЬНАЯ основа, только для чтения. Перед сборкой найди реальный
   экран в `qautomator-ui/src/pages/` (через `wiki/product/screens-map.md`), разбери структуру,
   состояния, компоненты. Переноси разметку и иерархию, но не копируй React-код — пиши свой
   HTML/CSS/JS. Если аналога нет — помечай явно как новый экран и согласуй.

## Чего не делать

- Не добавляй функциональность, которой нет в сценарии.
- Не стилизуй «от себя» — если чего-то нет в DESIGN.md, спроси.
- Не делай адаптив (прототипы смотрят на десктопе).
- Не пиши продакшен-код (без оптимизации, без accessibility beyond basics, без тестов).
- Не редактируй файлы монорепы.
- Не пытайся собрать весь flow одним промптом.

## Процесс

1. **Сценарий.** Прочитай сценарий из `wiki/scenarios/`. Если неясно — спроси до генерации.
2. **Грунтовка по репе.** Найди реальный экран-аналог в `../qato/qautomator-ui/src/pages/`
   (через `wiki/product/screens-map.md`). Разбери layout, компоненты, состояния — это скелет.
   Если аналога нет — пометь как новый экран.
3. **План.** Перед кодом — план: экраны, состояния, переходы. Цель сценария — в начале плана.
   Сошлись на экран-основу из шага 2.
4. **Сборка по шагам.** Один экран/состояние за итерацию. Скелет — из репы, стили — из DESIGN.md.
5. **Проверка после каждого шага.** Открой HTML, сверь с DESIGN.md, сценарием и структурой
   реального экрана. Исправь расхождения до следующего шага.
6. **Финальная сверка.** Сравни с исходным сценарием. Найди пропущенные состояния и edge cases.
7. После сборки — обнови хаб `wiki/tasks/QATO-XXXX.md`: ссылка на прототип, статус. Прототип
   идёт в дизайн-спеку (QATO-452, см. `wiki/references.md`).
8. **Локальный просмотр пользователем.** ⚠️ Чтобы прототип открылся в Chrome пользователя на
   `localhost:<port>`, сервер ОБЯЗАТЕЛЬНО подними как фоновый процесс на хосте через Bash:
   `cd prototypes/QATO-XXXX-slug && nohup python3 -m http.server <port> >/tmp/protoXXXX.log 2>&1 &`,
   затем `open -a "Google Chrome" http://localhost:<port>`.
   **Не полагайся на `preview_start` (Claude Preview MCP) для показа пользователю:** он поднимает
   сервер в изолированном окружении — его внутренний браузер (screenshot/click/snapshot) туда достаёт,
   а Chrome пользователя на хосте `localhost:<port>` НЕТ (connection refused). preview_* годятся
   только для твоей собственной верификации; для пользователя нужен хостовый `http.server` через Bash.
   Проверь, что хост реально слушает: `curl -s -o /dev/null -w "%{http_code}" http://localhost:<port>`
   должен вернуть `200`. Порт держи уникальным (по номеру задачи, напр. 4671 для QATO-1671) — занятые
   порты см. в `.claude/launch.json` и через `lsof -nP -i :<port>`.
9. **Публикация (опционально).** Для удалённого показа — Cloudflare Pages (не GitHub Pages:
   репо приватный). Настраивается отдельно.
